# Audit reader calls and artifacts

This is the execution contract for Audit Step 5 and Step 8 readers. The shared verification ledger remains the evidence schema. This reference separates the two quantities the earlier procedure conflated:

- an **evidence row** is one complete role verdict for one claim or page;
- a **reader call** may return several evidence rows, but only for units with the exact same complete ordered raw path/SHA manifest and the same role.

Audit computes both quantities before dispatch. It uses separate numbered executions because bullet evidence is collected before repair while whole-page evidence must bind final post-repair bodies. It never discovers its claim/page arithmetic halfway through a run, narrows scope to fit a budget, switches to one reader per page, or asks whether to continue.

## Phase A: Batched Evidence Collection

0. Immediately after the exclusive Warning baseline is captured, run `manage_reader_batches.py journal-init 2-outputs/audit/reader-artifacts/{run-id}/execution-journal.json --run-id {run-id} --warning-baseline-sha256 {baseline file SHA-256}`. It requires a new empty run directory and exclusively creates both the baseline-bound empty journal and `execution-anchors/`. It refuses replacement or reinitialization when any prior run state remains. The report retains the journal's canonical path and exact file SHA-256 even when no reader execution is needed.
1. After final `READY(n)`, build the complete bullet unit input for `.claude/skills/audit/scripts/manage_reader_batches.py`. Every unit binds its exact claim ID, current ledger `context_digest`, exact ledger `raw_dependencies`, and `verification_scope: ordinary|exhaustive_negative`; the completion validator compares all four fields and the population directly to the terminal claim row. Classify every universal or exhaustive negative as `exhaustive_negative` and freeze its exact `quantified_population: {raw_paths, members}` before planning. `members` is ordered by raw path then member ID; each object is `{"member_id":"specific condition/task/run/source identity","raw_paths":["one exact raw path"]}`. Create one member per actual unit quantified by the claim, so ten conditions in one PDF produce ten members; every dependency raw has at least one member and no member spans raws. A generic container label such as `paper` is not a population member unless the claim truly quantifies specifically identified papers, in which case use each source identity. Compute the expected page rows/calls from current scope now, but wait for final post-Step-7 bodies before constructing the page execution.
2. Run `manage_reader_batches.py plan {input.json} {plan.json}`. The deterministic plan groups only identical full raw manifests. The limits are hard maxima, not coordinator preferences: at most 25 claims, 4 pages, and 4 concurrent calls. Both roles receive separate batches. Record the input SHA-256, plan SHA-256, evidence-row counts, call count, group count, and automatic wave schedule in the retained Audit report before launching anything.
3. Dispatch complete role batches. A reader receives only its role prompt, its batch units, the complete final pages and raw evidence for those units, and the exact plan/epoch binding. It never receives counterpart prompts, verdicts, cached rows, or adjudication.
4. Each reader writes one unique `{batch_id}.json` sidecar in the run's artifact directory. It returns to the coordinator only one compact receipt: batch ID, terminal state, record count, sidecar path, and sidecar SHA-256. It does not return full findings, quotes, or reasoning inline.
5. Run `manage_reader_batches.py collect {plan.json} {artifact-dir} {collected.json}`. Collection first reconstructs the original input and every plan count from its schema-exact batches, then rejects any missing/extra sidecar, stale plan/input/epoch binding, pooled or omitted unit, duplicate record, wrong role/generation/raw manifest, placeholder/truncated evidence, or reused agent/reader-run identity across blind counterpart roles. Keep the plan, sidecars, and collected artifact until the report is terminal.
6. Before importing any collected row, run `manage_reader_batches.py journal-append {journal-path} {plan.json} {collected.json}`, where `{journal-path}` is the exact canonical path Step 0 created. It validates the complete prior chain and exact anchor inventory, refuses duplicate plans, checks plan/collection identity and counts, atomically publishes the next numbered anchor without replacement, and then extends the journal. A partial temp is never published. Retry removes only an unpublished temp for the exact next number or a temp proven to be the final anchor's same inode; cleanup failure aborts before journal advancement. The helper never overwrites an anchor. If interruption lands after anchor publication but before journal replacement, the next identical append adopts exactly that one matching trailing anchor; any other mismatch fails closed. The completion validator independently requires anchor entries, journal entries, report executions, and exact artifact-root children to agree.
7. The collector proves transport and schema only. The coordinator reads every accepted full record from sidecar in bounded sequential slices, re-extracts each HOLD/REFUTE quote at its raw locator, semantically adjudicates it, and writes one digest-bound `reader_adjudications` object for every retained record, including superseded records, before importing terminal rows. All adjudications use one coordinator identity and run distinct from every retained reader identity and run. A clean receipt or Boolean prose attestation is never a substitute for this authenticated read.

Bounded slices keep full transcripts out of the coordinator's context at the same time; they do not remove the coordinator's responsibility to inspect every record.

## Exhaustive-Negative Proof

For `verification_scope: exhaustive_negative`, both bullet-role records carry this exact object:

```json
{"quantified_scope":{"raw_population":["every frozen raw path"],"population":["every frozen member the claim quantifies over"],"searched_members":["every member actually searched"],"counterexamples":[],"search_summary":"aliases, terms, regions, and result"}}
```

A HOLD requires `raw_population == quantified_population.raw_paths`, `population == [member.member_id for member in quantified_population.members]`, `searched_members == population`, and no counterexample. A REFUTE requires at least one exact counterexample from the searched population. A missing/unreadable member cannot HOLD and ends `cannot_confirm` unless another member already refutes the universal claim. Readers cannot shrink either population in their result. The collector enforces this mechanical boundary; semantic adjudication still belongs to the coordinator.

## Phase B: Repair and Certification

Non-HOLD evidence creates exact repair obligations. Apply determinate repairs under Step 7, invalidate affected units (or the whole relationship epoch when required), and build a numbered execution over every final page plus only the bullet roles invalidated by repairs. A destructive correction or removal is forbidden unless both blind roles REFUTE and one third agent/run, distinct from and blind to both, writes `reader-artifacts/{run-id}/destructive-reviews/{claim_instance_id}.json`. The report binds that sidecar's exact payload and file SHA-256 in `destructive_correction_reviews`; approval is mandatory. Step 8 consumes final collected records, runs the central locator/relationship checks, and performs terminal status/hash writes. Every execution is journaled before import and partitions all collected row IDs into `terminal_row_ids` and `superseded_rows`. An ordinary superseded row names a retained same-role terminal replacement; the two unanimous REFUTE rows for a removed claim name the exact validated destructive-review row instead, because the removed claim and its verdict rows cannot appear in the final current-claim ledger. The completion validator checks the journal census, enumerates every direct artifact-root child and numbered execution directory, replays all sidecars, retains invalidated work as auditable cost, and requires terminal reader records alone to equal the final ledger rows. There is no public skill handoff between phases: the incomplete report, run ID, baseline, epoch, manifests, and artifacts are one recoverable transaction.

## Recovery

On restart, accept an existing plan or sidecar only after the helper recomputes and validates its exact hashes, journal, and write-once anchor inventory. Relaunch only missing/rejected batch IDs. Never reinitialize a run whose anchor state remains, and never credit a receipt without its validated full sidecar, a sidecar from another epoch/generation, or a late result from an invalidated epoch. After Step 4a closes, Audit exclusively freezes every maintained page in `2-outputs/audit/baselines/audit-{run-id}-preverification.json`; its path inventory must equal the Step 1 baseline. Before the first Step 4b or Step 7 content edit to an existing scoped page, copy its exact checkpoint bytes and metadata into `content_rollback_preimages`; for a new split-off path, retain a checkpoint-authenticated `preimage_existed: false` row. If a reader/tool/service failure remains after safe retries, restore each existing page byte-for-byte to that checkpoint, remove each newly created path, set `rollback_required: true`, list every affected path in `infrastructure_failure_pages`, and run `validate_audit_completion.py {report} --repo-root . --verify-incomplete-rollback` before finalizing `incomplete` without a question. This preserves completed Step 4a neutral work while removing every later partial edit; status, hashes, and markers are never changed as an infrastructure disposition. Raw unreadability is an evidence result and follows the separate `needs-update` rule; infrastructure failure is not evidence and never demotes a page.

The journal and anchors provide fail-closed local recovery and deletion detection while either retained state remains. They are not cryptographic non-erasure against an actor that deliberately deletes the report, journal, anchors, and every execution artifact from an entirely mutable uncommitted worktree; no local validator can prove evidence that has all been erased. A stronger guarantee requires a user-authorized committed or external checkpoint and is outside Audit's current transaction.
