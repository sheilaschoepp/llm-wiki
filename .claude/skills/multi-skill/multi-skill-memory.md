## 2026-07-26 — the source-attachment demotion is inherent; eight designs to remove it were refuted

Binds `ingest`, `audit`, `supersede`, `forget`, `lint`. Attaching a source to a `verified` concept/entity/synthesis page demotes it, so the re-earn re-runs the tiered gate over the whole page. Eight independent designs to avoid that cost were refuted across two five-member councils and four mechanism refuters (audit trail: `2-outputs/skill-llm-council/skill-llm-council-2026-07-26-0414-gate1-attachment-change.md` and its addendum). Do not re-attempt these without new ground truth: (a) making the `Sources`-callout append a verification-neutral allowlisted edit — every allowlist entry preserves what the reader reads, this is an insertion, and `CLAUDE.md` (Source Support And Verification; Concepts and Entities) says the `sources:` frontmatter and `Sources` callout *carry the page's overall support*, so the append asserts a fact only the raw can settle; (b) a support-pending marker on the callout entry, in any settlement form — the support question cannot be put to a refuter (refuters get the claim and the raw, never the page's framing; there is no page-level tier; a no-quote relevance verdict is dropped); (c) riding prior certification across a demotion via a preserved hash — a body-identity proof cannot express "this body is unchanged and that is exactly the problem", which is precisely what audit's criterion-tightening, anti-decay, distortion-disposition, and suspected-raw-divergence demotions all are. Two facts settle most re-attempts: `sources:` is **not** in the hash-safe "mechanical metadata" enumeration (`updated:`, `source_count`, index/log are), and `supersede/SKILL.md` already rules that a `verified` merge survivor gaining a source demotes "even though the moved-in content bullets stay marked `*[unverified]*`" — the marked-bullets-carry-the-load argument is adjudicated. Settled 2026-07-26 by user decision: `source_count` counts **distinct underlying works** everywhere (two `sources:` entries whose `file:` resolves to the same raw count once), which also let `synthesis_under_supported` enforce the two-source floor mechanically for the first time — the schema's old carve-out is retired. Also landed: `verified_sources_changed` (a git-HEAD diff-guard catching a `sources:` change on a verified page, which `verified_hash` cannot see because frontmatter sits outside it) and a raw-drift check in audit Step 3 (git-based, no stored state). What remains open: narrowing the *re-earn's raw-side work* (the coverage gate and the no-sampling cross-source locator sweep currently re-run against **every** listed raw, though only one raw is new and no existing claim's text changed) — the coverage gate and the no-sampling cross-source locator sweep still re-run against every listed raw. (The under-enforcement half is closed: `verified_sources_changed` catches a `sources:` change on a verified page whether or not the callout was synced.) Strong graduation candidate for `MEMORY.md` once it has survived a later session.

## Report-naming convention (all skills, one format)

Every report-writing skill writes a dated operation report to its own `2-outputs/<kind>/`, named `<kind>-YYYY-MM-DD-HHMM(-<seg>)?.md`. `<seg>` is the skill's per-run label (topic, slug, stem, target, or skill-name); `audit`, `lint`, `consistency`, and `cleanup` use no seg, and `audit` may add a `-full` mode marker. Get the stamp once per run with `TZ='UTC' date '+%Y-%m-%d-%H%M'`, never a bare `date`. The format is uniform across every skill and is enforced by `file_naming_consistency` and `output_kinds_match_disk`. One deliberate exception: `checkup` is a pure orchestrator that writes no report of its own, since its consistency, lint, and audit sub-runs each write theirs. The convention lives here, in each skill's own body, and in those two checks, so it need not be duplicated into every skill's `description:` frontmatter.
